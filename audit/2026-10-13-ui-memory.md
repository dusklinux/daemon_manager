# Control Center and App Library memory comparison — 2026-10-13

Device: rootless-jailbroken iPhone 8 Plus, iOS 16.7.16. This tests the existing companion's presentation/capability hooks, not removal of either framework or disabling SpringBoard/backboardd. App v1.0.26 and all saved daemon settings remain unchanged.

## Idle comparison

The user turned the screen off and left the phone untouched. Eight fresh SpringBoard launches used this mirrored order: both Off, Control Center On only, both On, App Library On only, App Library On only, both On, Control Center On only, both Off. Each launch settled for 60 seconds after the new PID/current-PID companion report appeared, then supplied three approximately 10.2-second resource intervals. Each combination therefore has two independent launches, not six independent trials. Both hook support flags were true and the applied flags matched the requested state in every trial. Every recorded display brightness was 0 and idle-state value was 5.

The read-only libproc sampler measures physical footprint via RUSAGE_INFO_V2 and CPU via PROC_PIDTASKINFO with the device's Mach timebase. It also records vm_stat and the native memory-pressure flag. No memory stress, app eviction, kernel reboot, daemon override or companion removal was applied. Resprings restarted SpringBoard and backboardd. The same companion stayed installed in all conditions, so this does not measure its overhead against having no companion.

| Enabled interfaces | SpringBoard mean footprint (MiB) | Two launch means (MiB) | backboardd mean footprint (MiB) | SpringBoard / backboardd mean CPU (% of one core) |
| --- | ---: | --- | ---: | --- |
| Neither | 62.314 | 62.189, 62.439 | 24.319 | 0.142 / 0.466 |
| Control Center only | 62.441 | 62.428, 62.454 | 23.972 | 0.192 / 0.463 |
| App Library only | 63.139 | 62.876, 63.402 | 24.860 | 0.420 / 0.508 |
| Both | 63.470 | 63.236, 63.704 | 25.064 | 0.167 / 0.475 |

SpringBoard's mean both-On minus both-Off difference was **1.156 MiB**. The corresponding differences within the mirrored passes were 1.047 and 1.266 MiB. Enabling App Library increased SpringBoard's mean by 0.826 MiB with Control Center Off and 1.029 MiB with Control Center On. Enabling Control Center increased the means by 0.128 MiB with App Library Off and 0.331 MiB with App Library On. Control Center's tiny difference is too close to launch variation to promise as a dependable saving. App Library/both-Off showed a small repeatable SpringBoard difference in these two passes; this is not a universal allocation guarantee.

backboardd varied between launches (including 23.9–25.8 MiB across App Library-only launch means). Its group means are descriptive, not a proven saving attributable to these hooks. Do not add process footprints and call the sum free RAM.

The vm_stat Pages free counter averaged 476.612 MiB for both-Off and 476.081 MiB for both-On; individual launch means varied from 461.193 to 486.036 MiB. Speculative pages grew with time, and compressor occupancy stayed around 37.7 MiB. These overlapping/drifting counters do not establish a net available-RAM gain. The vm_stat printed Pages free value excludes speculative pages; the app’s host_statistics64 free_count includes them. This distinction follows [Apple’s vm_stat implementation](https://github.com/apple-oss-distributions/system_cmds/blob/main/vm_stat/vm_stat.c). Do not mix those counters or count speculative pages twice. Memory pressure was Normal (flag 1) in all 24 intervals. There was no sustained high-CPU retry loop in these short samples. No battery-life or long-term stability result is claimed.

Per-launch means are in [ui-memory-2026-10-13.csv](ui-memory-2026-10-13.csv). Raw finite samples, original settings, native override backup and experiment scripts are private under the workstation audit-private/ui-memory directory and the phone's Documents/daemon-audit-2026-10-13/ui-memory directory.

## First-use check

Both interfaces were then enabled in a fresh launch (SpringBoard PID 5821), settled for 60 seconds, and sampled three times. The user opened Control Center for about 10 seconds without changing toggles, closed it and turned the screen off. After 30 seconds of settling, three more samples were taken. The user then browsed App Library categories and its alphabetical list, returned Home and turned the screen off; the same settling/sample protocol followed. The user explicitly reported that the alphabetical list also opened the keyboard. All three phases retained the same SpringBoard/backboardd PIDs, applied On flags, display brightness 0 and Normal memory pressure.

| Same-process phase | SpringBoard mean footprint (MiB) | backboardd mean footprint (MiB) |
| --- | ---: | ---: |
| Before opening either panel | 64.486 | 23.657 |
| After Control Center, closed | 65.642 | 26.428 |
| After App Library categories/list plus keyboard, closed | 68.616 | 28.642 |

Control Center/wake/Home interaction left a 1.156 MiB SpringBoard increase. The later App Library/list/keyboard/wake/Home interaction left a further 2.974 MiB increase, or 4.130 MiB above the initial baseline. These are retained footprints over the observed post-use intervals, not permanent allocations or clean per-feature savings. Keyboard use is an explicit confounder; do not attribute its allocations to App Library. This additional fresh both-On launch started above the two idle-pass both-On footprints, further illustrating launch variability. No precise net-free-RAM, reclaimed-cache or battery gain follows from these figures. The process-level phase means are recorded in [ui-memory-use-2026-10-13.csv](ui-memory-use-2026-10-13.csv).

A second fresh both-On launch (SpringBoard PID 5890) used the same initial settle/sample protocol. After the user confirmed browsing only the category screen for about 10 seconds without opening the list or keyboard, the post-use settle/sample protocol was repeated. SpringBoard's mean footprint rose from **64.111 to 67.199 MiB (+3.089 MiB)**; backboardd rose from **23.569 to 26.480 MiB**. Both PIDs remained unchanged, the screen was off, and memory pressure stayed Normal. SpringBoard had a transient 1.190% of one core in one interval, followed by 0.158%; this did not resemble the previous sustained one-core dependency failures. This single pair includes wake/Home interaction and background work during the user-response interval. It is not a clean allocation breakdown or a general reclaimable-memory promise.

Similar approximately 3 MiB SpringBoard growth without the keyboard shows that the keyboard was not required for the observed post-use growth. Do not subtract results from different process launches to calculate the keyboard's precise contribution. These first-use results show that idle startup measurements do not capture every allocation incurred by opening the panels. They do not establish that all related services, metadata stores or caches stop with the interface Off. Reclaim under pressure, long-term cache behavior and battery effects remain untested.

## Restoration

After the first-use checks, the exact original preference bytes were restored and SpringBoard resprung. The current-PID companion report (PID 5943) confirms both hooks supported and both interfaces Off. The native saved daemon override map parsed identically to its pre-test backup. No app rebuild is required for this measurement/documentation-only update.

After the same 60-second settling period, three final screen-off samples measured SpringBoard at **62.491 MiB**, backboardd at **23.777 MiB**, with mean CPU **0.168% / 0.465% of one core** and Normal pressure throughout. This is a recovery check, not another independent proof of net RAM/battery savings. All finite samplers completed; no resident monitor was installed. Only iOS repository documentation/data and local reference Markdown notes were changed; daemon targets, the companion source, app version and Linux Git index were not changed.

## Subsequent user decision: default and current state On

After reviewing the measurements, the user requested keeping Control Center and App Library On by default. The existing app already uses false disabled flags for both when preferences are absent; no source/default migration or new IPA is required. Saved explicit Off choices are intentionally preserved by read operations and app installation/updates, so the phone's two saved flags were explicitly set false for this user decision and SpringBoard resprung. Manual Off controls remain available.

The new current-PID runtime report (SpringBoard PID 5985) confirmed both hooks supported and both disabled flags false. Respring returned 0; the native saved daemon map parsed identically to the pre-change backup. Original interface preferences and native map were saved separately in the phone's Documents/daemon-audit-2026-10-13/ui-defaults directory; verification was copied privately to the workstation. No kernel reboot or daemon override was applied. Existing three UI-control tests passed, and a focused absent-preference fixture confirmed both interfaces default On without writing a preference file. This change does not claim a RAM/CPU improvement: it restores interface access according to the user's preference. Historical Off-restoration measurements above remain valid for the experiment, not the final live state.
