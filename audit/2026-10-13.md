## Coverage and limits

Source review covered presets/descriptions, enumeration, override execution and verification, root commands, UI groups, memory/stress, diagnostic restoration, helpers, tests, project configuration and CI packaging. Byte integrity is not proof of functional correctness.

509 installed launchd plists represent 507 unique labels. Two files export the same CommCenter label, and two export the same nanoregistryd label. Of 512 preset entries, 496 match an installed Label exactly; 16 are absent/filename/legacy aliases. The complete per-target inventory is [services-2026-10-13.csv](services-2026-10-13.csv). Its baseline fields describe the starting phone, while target/classification columns reflect the current builtins; they intentionally differ. The v1.0.25 logging follow-up updates the two actual DNS-label classifications without changing their On targets. `None` means no explicit saved override. Missing overrides, registered jobs and running processes are distinct states. Footprints are process readings, not guaranteed reclaimable memory, and are never summed as a RAM-saving estimate.

At baseline, the system and mobile disabled maps each exposed the same 330 entries, 315 disabled. They must not be counted as 630 disabled services. No disabled installed job was still registered; no enabled installed job matched the old preset's Off list. The recent reference's reset-era state was therefore not the whole current profile. This audit did not reapply an old profile or retest the previously established feature groups.

The source, native state inventory and sampled workloads were inspected comprehensively within this scope. An exhaustive empirical test of every service and every combination was not performed. Neither this report nor the `yes` preset values establish universal safe disabling. Apple publishes no complete public dependency graph for these private jobs. Raw device logs, preferences, credentials and full stack reports are excluded from the repository. ## Isolated siriactionsd test

The starting siriactionsd process used 6,449 KB, about 6.30 MiB. Its plist points to VoiceShortcuts and exports `com.apple.siri.VoiceShortcuts.xpc`, Shortcuts dialogs, automation notifications and account/paired-sync endpoints. It is not simply a voice-assistant worker.

Only `com.apple.siriactionsd` was newly disabled, using native launchctl in its observed mobile domain, followed by `launchctl reboot userspace`. Its saved override persisted and `launchctl print` returned 113: no registered job. The user confirmed Home/unlock, typing, WhatsApp, and taking/viewing a Camera photo still worked normally. No other saved override changed versus the pre-audit backup at the comparison checkpoint.

Two 15-second all-process stackshots captured startup and interaction; they did not reproduce a sustained one-core client retry loop. They are not equivalent idle benchmarks. A subsequent finite, lower-overhead libproc sampler measured three locked intervals of approximately 10.15 seconds. Backboardd used 0.497%, 0.517% and 0.483% of one core; pressure flags were 1 (Normal) throughout. Mach ticks were converted with the device's measured 125/3 ns timebase. Core processes remained present. These observations support removing the unconditional historical CPU assertion and making siriactionsd default Off for this requested profile. They do not establish overnight stability or every Shortcuts/app-intent path.

The disappearance of a 6.30 MiB process footprint is observed. Net physical-free RAM gain and battery-life improvement were **not established**: caches, app activity and userspace restart changed the memory categories. Shortcuts and automations using this broker intentionally stop working while it is Off. Restore the existing Shortcuts group On and restart userspace before using them. The new Siri group also includes ShortcutsUI; its established Off policy remains available without a new UI-host experiment.

`searchd` remains enabled. It serves Spotlight/Photos queries and is not a Siri-only service. Its older individual CPU causality was already unproven; that is kept explicit. Biome, context/scheduling, pkd, preferences, account, Photos conversion and other repaired shared dependencies remain protected. This session's isolated experiment establishes a narrower result than disabling all shared brokers together.

## Backboardd investigation

The interaction sample used 1.745 CPU seconds in 15 seconds (11.6% of one core). A targeted symbolicated screen-on sample used 1.243 seconds in 15.01 seconds (8.3%). After the user locked the phone, the same PID used 0.073 seconds in 15 seconds (0.49%); the main and HID threads were mostly waiting, with render-server CPU time only 0.002 seconds. The independent libproc intervals agreed at roughly 0.5%. Thermal pressure stayed 0.

This supports display/input-related activity rather than a persistent locked-idle CPU loop in the sampled period. It does not establish a universal threshold for healthy screen-on activity. Backboardd stays enabled because it is core input/display infrastructure.

## Source and classification corrections

| Finding | Change / evidence |
| --- | --- |
| Failed override refresh retained usable stale state | A failed read now clears the state; switches cannot operate on that stale snapshot. |
| Batches/restarts could overlap individual operations | Busy checks now cover those paths; action state is set synchronously before starting work. Existing parallelism within a batch remains. |
| Passwords were interpolated into a shell expression; su received already escaped commands | Sudo is spawned directly, credentials travel over stdin, and both sudo/su receive the original command unchanged. Literal-character and signalled-child tests exercise the forwarding. |
| Process pipes could be inherited by another concurrent helper | Pipe descriptors are close-on-exec, with explicit child dup actions. Password writes handle short writes/EINTR and do not emit SIGPIPE on a closed reader. The installed kernel accepted F_SETNOSIGPIPE. |
| Historical power/bootloop assertions appeared unconditional | The unreproduced usermanagerd/nanoregistryd/sleepd/rapportd/nesessionmanager assertions now identify their historical origin. Their existing keep-enabled policy remains. BT LE power-saving language no longer implies a measured net gain. |
| rtcreportingd was described as a SIP server | The actual plist establishes a reporting helper and `com.apple.rtcreportingd` endpoint, not that role. The description was corrected. |
| heartbeatd was assigned a watchdog role without evidence | The description now states its observed helper/endpoint without that assertion. Anomaly-detection feature coverage is also qualified. |
| SSH disabling was described as permanent | The warning now correctly explains loss of remote access and local/alternative recovery. |
| Same phone process sometimes reported zero RSS/CPU in ps | The review uses spindump and libproc/Mach accounting. The new finite sampler is read-only and adds no resident polling service. |

The existing disk collector restores originally disabled jobs, but does not promise an exact restoration of every originally enabled/unregistered job. Its longer collection/lifecycle behavior was not rerun here. The emergency reset is still a broad launchd database reset rather than an exact per-service rollback. Those operations are not RAM optimizations.

## New groups and defaults

Bluetooth, Calls and SMS, Wi-Fi, Keyboard, Safari services, Location, and Siri and dictation have separate menu/subpage On/Off controls. Installed labels and exported endpoints were inspected. Explicit Critical opt-outs are limited to the Bluetooth profiles, listed call/SMS brokers and kbd. They do not weaken the existing groups' protections or disable shared prerequisite-only jobs. Existing group policy tests remain in place.

The new core-feature groups were **not** subjected to a full Off → userspace restart → functional failure/recovery cycle. The user requested these essential features stay working now and wanted the controls for future use. Their notes state this limitation. The controls save verified native overrides; Bluetooth/Wi-Fi service Off does not prove hardware radio power-off. Safari/WebKit and InputUI include app/XPC/interface processes outside these service groups, so no complete browser block or keyboard UI removal is claimed. Calls Off can affect cellular data, CallKit/VoIP and account verification. Wi-Fi Off can disconnect Wi-Fi SSH; restore locally or over an independently working USB connection.

Current builtins: **512 entries, 315 Off / 197 On, 90 Critical enabled entries** (including the two actual DNS-label corrections in the logging follow-up). Siriactionsd and ShortcutsUI now default Off. Actual SMS/Identity credential/attachment job labels and local Safari history/bookmarks now default On, matching the request to retain those features. Main Wi-Fi/Bluetooth/call/keyboard/camera/Photos/charging/SSH prerequisites remain On. Optional Siri, cloud sync, recording, telemetry and existing optional hosts retain Off targets. Shared OS services with no demonstrated reliable Off state are not blindly disabled.

Installing the IPA never applies these targets. Explicit custom defaults remain explicit. The legacy full-copy migration accounts for the revised inherited values. On a phone with manual choices, inspect Defaults before deliberately applying it.

## Delayed locked-idle failure and isolated recovery

The final user-locked check changed the conclusion. Three 10.15–10.16-second intervals measured assetsd at **105.633%, 105.581%, 105.592% of one core** while backboardd fell to 0.618%, 0.605%, 0.553%. Pressure remained Normal, so memory pressure alone did not expose this CPU failure. A targeted 5-second symbolicated stack sample independently measured 5.280 CPU seconds (105.6%). It showed Photos syndication/background SQL work, repeated CoreSpotlight query-failure completion, PLBackgroundJobSyndicationSyncWorker and PLSyndicationSyncManager callbacks. Repeated query queue identifiers progressed during that sample. No complete restart or other override change intervened.

Only searchd was enabled and bootstrapped again in user/501. The **same assetsd PID 5006** immediately fell to **0.009%, 0%, 0%** across three further locked intervals. searchd itself used 0.015%, 0.004%, 0%; backboardd stayed at 0.532%, 0.478%, 0.515%. This isolated Off → delayed failure → On recovery establishes the dependency on this tested profile more strongly than the earlier broad-unload and short foreground comparisons. It does not identify every exact background scheduling condition or claim universal behavior across other iOS releases.

Final state: searchd enabled, six previously disabled optional search-group jobs still Off, Siri/ShortcutsUI Off. The newly introduced searchd false override is an explicit enabled state; the initial backup lacked an explicit entry. No native plist was rewritten to erase that distinction. Both diagnostic jobs remain restored Off/unregistered. No kernel/full reboot was performed. Users can unlock/use the phone normally now.

v1.0.24 keeps the separate Spotlight group and all builtin targets, but corrects its warning and Critical searchd description to identify the reproduced delayed failure and recovery. A deliberate group Off remains available as requested; it can increase CPU/battery use and is unsuitable for this normal Photos profile. Earlier v1.0.23 notes about unreproduced sustained CPU apply only to the initial short samples and are superseded by this result. This is a reliability finding and avoided CPU cost, not proof of increased free RAM or longer measured battery life.
